# Following Twitch and Kick streamers

Opening a stream checks its follow status once, including when opened in the background. The button shows **Checking…** while reading your platform website account, **Following** for an existing follow, and **Follow** otherwise. Click **Following** to unfollow, or **Follow** to follow, beside **Clip** in the playback toolbar. The button also works for a past broadcast with a known broadcaster. A pasted Twitch video whose broadcaster has not been resolved cannot be followed using its video ID.

The action uses your platform website account. On first use, sign in in the app's browser and select **Continue**. Canceling keeps the action unconfirmed. If Twitch requires further browser verification, the same channel page opens inside the app. Complete any Twitch check and click its Follow control; the window closes only after server confirmation. Closing or canceling that window leaves the follow unconfirmed. Twitch follows use their own website profile at `%LOCALAPPDATA%\StreamStudio\TwitchFollowsWebView2`, separate from background channel-point bonuses; Kick reuses the profile used by **Detect Kick follows** and clips. OAuth connections and website sign-in are separate. Twitch's Following page is loaded for the connected OAuth account, so use the same Twitch account in both sign-in flows.

**Following** appears only after server confirmation. Clicking it unfollows the selected broadcaster; the button returns to **Follow** only after the platform confirms the change. Automatic status checks never prompt for sign-in or send a follow/unfollow request. Switching tabs leaves pending checks running and reuses completed attempts, including failed or unverified attempts. Closing a tab cancels its check; closing and reopening the stream checks again. Changes made on the platform website are picked up on reopening. A late response cannot overwrite a different channel or a newer follow/unfollow change. The tooltip and accessible name describe the current action. Switching or closing a stream while a follow/unfollow request is running never changes the broadcaster being followed. The app refreshes the Following library after either change, in the background; loading library metadata does not keep the follow button busy. A verified Kick follow-list snapshot replaces imported follows and saves automatically; manually added Kick channels are preserved. Import, clear, follow, and unfollow operations are serialized so an older import cannot overwrite a follow. A failed local save is reported separately from an already-confirmed platform follow.

## Verified platform contracts

Inspected on 2026-10-08 using current first-party documentation and the scripts loaded by the channel websites:

- Twitch [retired its follow/unfollow API](https://discuss.dev.twitch.com/t/deprecation-of-create-and-delete-follows-api-endpoints/32351). Its [current API reference](https://dev.twitch.tv/docs/api/reference/#get-followed-channels) provides follow reads, rather than a supported follow-write endpoint.
- Twitch's [follow controls](https://assets.twitch.tv/assets/7034-daf68acf50c3a9ebafdf.js) use `data-a-target="follow-button"`, a localized `Follow {displayName}` accessibility label, and distinct unfollow controls. The [main channel's button wrapper](https://assets.twitch.tv/assets/11658-208d5da17e24cd4fe4ba.js) passes that display name to the control. The [channel layout and website mutation](https://assets.twitch.tv/assets/core-b47f8bda3872513d1495.js) put the main channel's live and offline controls inside `.channel-info-content` and use `FollowButton_FollowUser`, with `variables.input.targetID`; its payload includes `followUser.error` and the followed user. The [user fragment](https://assets.twitch.tv/assets/27599-31a487948d870cac0af7.js) includes the login, ID, display name, and `self.follower.followedAt`. The app selects the main channel's control, checks its name, blocks unexpected target IDs and duplicate follow writes before networking, handles GraphQL and platform errors, and requires a server follower timestamp.
- Kick's [public channel API](https://docs.kick.com/apis/channels) has no follow-write operation. The [channel controls](https://assets.kick.com/main/_next/static/chunks/165qqxtqp1t-k.js) identify their follow button with `data-testid="follow-button"`. Its [button wrapper](https://assets.kick.com/main/_next/static/chunks/3ftqejh-6hm6i.js) updates following state optimistically. The [website channel API](https://assets.kick.com/main/_next/static/chunks/0w9432yhv2j_b.js) uses `POST /api/v2/channels/{slug}/follow` and paginated `GET /api/v2/channels/followed`. The app reads the complete list before clicking and again after the POST succeeds. An HTTP acknowledgement or a changed icon alone cannot confirm success.

These asset filenames record the inspected deployment; the app does not load those files directly or hard-code their mutation hashes. It lets each website issue its own authenticated follow request through its current button. Twitch unfollow opens the selected channel's unfollow control and confirms only its broadcaster-matched dialog; `FollowButton_UnfollowUser` must return the same user with `self.follower: null`. Kick unfollow uses the website's authenticated `DELETE /api/v2/channels/{slug}/follow` contract, keeping the session token inside the browser origin, then rereads every page of the follow list and requires the broadcaster's absence. Both follow and unfollow guards reject writes for another broadcaster, writes in the opposite direction, and repeated mutations. A status-only browser rejects all follow writes. Hidden browser media is blocked and muted. Ambiguous controls and navigation to another channel stop the action. A page reload after dispatch also stops verification without clicking again. Session fingerprints are checked before clicking and before accepting the result. Website tokens are neither saved in settings nor included in messages or logs.

### Status and unfollow contracts, 2026-10-20

Rechecked the first-party [Twitch channel bundle](https://assets.twitch.tv/assets/core-b47f8bda3872513d1495.js) and [follow controls](https://assets.twitch.tv/assets/7034-daf68acf50c3a9ebafdf.js): the unfollow confirmation is `data-a-target="modal-unfollow-button"`, its dialog identifies the broadcaster, and the mutation uses `FollowButton_UnfollowUser` with `variables.input.targetID`. Its `unfollowUser.follow.user` includes the same follow fragment; unlike the follow mutation, the unfollow payload does not require an `error` field. Kick's [channel API bundle](https://assets.kick.com/main/_next/static/chunks/0w9432yhv2j_b.js) specifies the same follow route with method `DELETE` for unfollow. The app never interprets an HTTP acknowledgement, optimistic client state, or a button icon as proof of either change.

### Integrity challenge correction, 2026-10-20

An authenticated reproduction of the reported Twitch failure returned HTTP 200 with a GraphQL `failed integrity check` error, `data.followUser: null`, and `extensions.challenge.type: integrity`. The previous implementation treated this as a terminal error and disallowed the website's subsequent request as a duplicate. Twitch's current [website challenge link](https://assets.twitch.tv/assets/95120-2b98dafa4e10f6c12607.js) refreshes its own integrity token and replays the rejected operation. The app now permits one such website retry only after inspecting that explicit noncommitted response, rechecks the browser session, and still requires the selected broadcaster's server follower timestamp. Wrong targets, repeated mutations without a challenge, and account changes remain failures. A WebView2 request deferral orders a fast website retry behind response inspection; the app does not obtain or construct integrity tokens itself.

The authenticated retest also established that Twitch can reject its own refreshed integrity token in the embedded browser. A repeated integrity rejection or an interactive challenge now exposes the existing muted channel document in an in-app verification window instead of discarding it. After a repeated integrity rejection, only a fresh trusted click on the selected channel's Follow button can authorize another attempt; a synthetic click cannot. The account fingerprint and target checks still apply. The app allows five minutes for verification and never treats the window opening, closing, or a button icon as success. Twitch must still accept its browser checks; this flow cannot guarantee acceptance by the platform.

The user then reproduced the rollback in a plain WebView2 channel page with the old profile, with no app scripts, request inspection, or resource filters. A fresh in-app profile accepted sign-in and the follow. Twitch follows therefore no longer reuse the background bonus profile. The original bonus profile is preserved, and no website cookies or tokens are copied between the profiles.

The final authenticated check used the production `ChannelFollowService` with its default browser creation and the dedicated profile. It followed a second user-selected Twitch channel and obtained server confirmation. A second service invocation confirmed the persisted follow after loading the channel in a new controller. This check used no diagnostic request interception or DevTools instrumentation.

### Unfollow control correction, 2026-10-20

The reported `deansocool` unfollow failure was reproduced with the signed-in production service. The application log recorded both ambiguous controls and a control that did not identify the broadcaster. Inspection of the authenticated channel document established that `.channel-info-content` contains both `aria-label="Unfollow Deansocool"` and an About control with `aria-label="Unfollow "`. The unnamed control can appear before the named one. The script now identifies candidates using the server-provided display name before checking for duplicates, and waits for the named control when the page is still rendering. Two matching controls still fail without a mutation.

The same live diagnosis established a separate opening failure: the initial click on the named control produced no confirmation dialog or unfollow request. The same DOM element remained connected, and a later opening click produced the confirmation. Opening a dialog and submitting its confirmation are separate phases. The app rechecks the channel, account, named control, and absence of a confirmation before requesting that noncommitting opening again. An existing confirmation is verified before its single submission; a dispatched mutation is never repeated by this polling. Twitch's actual confirmation uses `role="alertdialog"`, which is also recognized by the trusted-input verification listener.

The final authenticated retest used the production service with its default browser creation and the dedicated saved profile. `UnfollowAsync` obtained server confirmation that `deansocool` was no longer followed. A separate `GetFollowStatusAsync` invocation loaded a fresh controller and independently confirmed `IsFollowing: false`. This final check used no diagnostic request interception or DevTools instrumentation. All 41 follow tests passed, including regressions for concurrent named and unnamed controls, delayed named controls, an ignored dialog opening, one submission while its response is delayed, duplicate named controls, a mismatched confirmation, and trusted versus synthetic input in an alert dialog.

### Partial Twitch follow responses, 2026-10-20

The subsequent follow failure was reproduced with the signed-in production service for `deansocool`: it stopped with "Twitch does not allow this account to follow the selected channel." A read-only inspection of the same channel established that `PlayerTrackingContextQuery` returns `self.follower` without `self.canFollow`, before `FollowButton_User` returns `canFollow: true`. `EmotePicker_EmotePicker_UserSubscriptionProducts` also omits the permission field. The tracker treated an omitted GraphQL field as `false`, causing a false account restriction or erasing a permission established by an earlier response.

Follow permission now has three states: unknown, allowed, and denied. Only explicit JSON booleans change it; partial responses preserve an established value, and navigation clears it to unknown. The follow browser waits for an explicit allowance before clicking and still rejects explicit restrictions. Status reads and unfollows do not need follow permission. Permission and follower data can arrive in separate responses for the verified broadcaster.

The new parser and WebView2 regression tests both failed before the correction. The browser regression supplies the partial player response first, delays the permission response while a clickable Follow control is present, and supplies another partial response while the mutation response is held. It requires zero writes before permission, exactly one mutation afterward, and server confirmation before success. A separate browser test requires zero writes for an explicit restriction. All 44 follow tests pass without skips. An authenticated follow of `deansocool` also obtained the correlated server confirmation.

### Ignored initial follow click, 2026-10-20

The default production service then exposed a second failure on `papaplatte`: its first scripted click left the named Follow control unchanged, and no `FollowButton_FollowUser` request reached the native response observer before timeout. The website's inspected follow handler can return without issuing a mutation until its component has the required broadcaster data. A DOM click and an actual outgoing request must therefore be tracked separately.

The browser now permits another click on the same verified channel control only while no native Twitch follow/unfollow request has ever arrived in that operation. It rechecks the account before each attempt and spaces ignored clicks by at least one second. Native request arrival is recorded synchronously, before awaiting response processing or account verification, and checked again after the account await. Once any mutation request arrives, automatic clicking stops even while the response is deferred. The existing guard still rejects duplicate writes, wrong targets, navigation and account changes; only the correlated server response can confirm success. Kick and Twitch unfollow use their existing click behavior.

A WebView2 regression reproduces the ignored initial click and holds the eventual mutation response for longer than the retry interval. It failed before this correction and requires two DOM clicks, exactly one native mutation, no additional clicks while that request is pending, and server-confirmed success.

The final authenticated check used `ChannelFollowService` with its default browser creation, saved profile and operation timeout. It followed `papaplatte` and obtained server confirmation. Separate status calls created fresh browser controllers and confirmed that both `papaplatte` and `deansocool` remained followed. These final checks used no diagnostic request interception, injected diagnostic scripts or DevTools instrumentation. All 45 follow tests passed without skips; the Release build and publish passed with warnings treated as errors, and formatting verification passed for the changed C# files.

## Validation

`ChannelFollowTestCatalog` covers automatic status reads without sign-in prompts or mutations, follow/unfollow round trips, stale status cancellation, failed unfollows retaining confirmed state, Kick unfollow snapshot persistence, opposite-direction request rejection, Twitch unfollow dialogs, protocol matching, batched GraphQL responses, malformed replies, provider errors, integrity challenge retries and their account checks, trusted versus synthetic input during in-app verification, verification cancellation and cleanup, expired sessions before and after dispatch, account changes, wrong targets, duplicate dispatch across reloads, script failures after dispatch, cancellation, late browser creation, imported-follow persistence, save failures, import concurrency, slow library refresh, VOD broadcaster selection, and toolbar bindings. Platform fixtures use real WebView2 with synthetic credentials in unique temporary profiles and intercept every request; they exercise the browser and server-confirmation flow without sending follows to Twitch or Kick. A separate loopback HTTP test sends a real browser POST and checks that request inspection preserves the transmitted bytes and the committed request body used for response correlation.

The first-party source inspection establishes the current contracts. Automated fixtures do not establish that a particular real account can pass the platforms' sign-in, account-verification, or browser checks. Authenticated live follow testing requires the user's chosen streamer and website sign-in.
