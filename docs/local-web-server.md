# LAN browser player

Open **Settings → Advanced → Playback tools → LAN browser server…** in the desktop app. Add a web account with a username and a password of at least 12 characters. Select the private Ethernet or Wi-Fi address shared with the other device, choose a port (default `18443`), and select **Start server**. The app opens the sign-in page in the Windows default browser. On a TV, Linux computer, phone, or tablet, open the displayed **HTTPS** address and sign in with a web account. The browser may first require trusting the server's local HTTPS certificate. Keep Stream Studio running on the Windows host. Closing the control window leaves a running server available; **Stop server** or exiting the app closes it. Each application launch starts with the server off.

## If another device times out

Keep Stream Studio running with the LAN browser server showing its HTTPS address. If a VPN is connected on the Windows host, enable its local network sharing option; Mullvad's `mullvad lan get` should report `allow` (`mullvad lan set allow` changes it). Also check that Windows Firewall allows the app on the Private profile and that the phone is on the same, non-isolated LAN rather than a guest network. A certificate warning means the device has reached the server; see Certificate setup below before signing in.

Web accounts are created, changed and removed in the desktop server window. Changing a password or removing an account disconnects its active sessions; **Disconnect all devices** revokes every session. Account records and browser preferences are saved under the current Windows user's `%APPDATA%\StreamStudio\web-users.json`. Passwords are stored as individually salted PBKDF2-HMAC-SHA-256 hashes with 600,000 iterations; plaintext passwords are not saved. A damaged account file prevents the account window from loading rather than silently replacing it. The browser URL contains no sign-in credential.

Existing PIN-era browser preferences have no account identity, so new web accounts start with default preferences. Old browser storage and shared web chat geometry remain untouched but are not loaded into a web account. Desktop connected accounts, follows, downloads and watch history continue to use the existing shared data.

The Windows host signs in through the same web account form as other devices. The session cookie restores a signed-in browser until logout or expiration.

## Certificate setup

The server creates a dedicated, five-year local CA for the selected IP address and a one-year RSA server certificate signed by it. Both private keys stay in the current Windows user's personal certificate store. The server control window displays SHA-256 fingerprints for the CA and server certificates. **Export public CA certificate** saves only the CA's public `.cer` certificate; it contains no private key. Compare the CA fingerprint before installing/trusting it on another device. The app does not change device trust settings automatically. A changed host IP needs a new CA and server certificate.

On iPhone, transfer the exported `.cer` to the phone and open it in Safari or Files. In **Settings**, tap **Profile Downloaded** and **Install**; installed profiles also appear under **General → VPN & Device Management**. Then enable **Full Trust** for **Stream Studio LAN CA** under **Settings → General → About → Certificate Trust Settings**. If the CA is absent there, the profile has not been installed. Return to Safari and open the displayed `https://` address. Enter the web username and password when the Stream Studio sign-in page appears. Tapping **Proceed** on a certificate warning may fail for a self-signed server certificate; the CA issued certificate is intended for explicit trust instead. See [Apple's profile installation](https://support.apple.com/en-us/102400) and [certificate trust instructions](https://support.apple.com/en-us/102390), plus [Apple Developer Technical Support's local CA guidance](https://developer.apple.com/forums/thread/764673).

There is deliberately no plaintext HTTP mode: passwords, session cookies, chat messages, and account-backed actions travel over HTTPS. Some TV browsers cannot accept local certificates, support Media Source Extensions/HLS, or decode a provider's video codec. Such a browser cannot use this player securely; the interface reports unsupported playback rather than claiming universal TV compatibility. Browser autoplay restrictions may require selecting Play. Browser picture-in-picture is offered only when supported.

## Browser functionality

Opening a stream shows a Twitch-style channel watch page with the broadcaster's real bio, follower count, tags, social links and original channel panels. See [channel content, controls and provider limitations](twitch-watch-page.md).

The browser interface has responsive workspace navigation, channel and URL search, Twitch/Kick and live-only filters, contextual loading/empty/error states, grouped player controls and explicit preference-save feedback. Press **Ctrl+K** (or **⌘K**) to open the direct stream dialog. Open live streams show their viewer counts in the sidebar. See the [browser experience changes and visual verification](web-experience-2026-10-21.md).

Twitch Discover category cards display viewer totals as they arrive, including zero viewers. Categories remain usable while totals load. An unsuccessful lookup displays **Viewers unavailable**; Refresh retries it. Totals also load for category searches and additional pages. Switching categories, queries, or platforms cancels pending lookups.

Twitch's HTTP 200 missing-art JPEG is detected by the server before reaching category cards. Missing covers show **Artwork unavailable** and can recover on Refresh after a 30-second failure cache expires. See the [Slots and Games + Demos investigation and browser verification](twitch-discover-artwork-2026-10-22.md).

- Twitch and Kick followed live/offline channels, automatic channel search with an inline dropdown, category discovery with pagination, channel video lists and video-type filters, recent streams and removal. Search suggestions appear after a 250 ms typing pause and keep the current library or player visible. Use arrow keys and Enter, or select a result with a mouse or touch; Escape dismisses suggestions. Live channels open playback; offline channels open their videos. See [channel search behavior and verification](web-channel-search-2026-10-22.md).
- Playback on the client device using native HLS or the bundled hls.js player. Provider manifests, variant playlists, segments, encryption keys, and initialization sections travel through authenticated, same-origin media routes. The browser never receives upstream signed media URLs or desktop account credentials. Low-latency HLS delivery directives are explicitly validated.
- Up to 16 players per device session, with a shared cap of 32 players across devices. Tabs can be selected, renamed, reordered, closed, or shown as a grid. Inactive players are muted unless Never mute is selected. Native browser controls provide pause, volume, mute and scrubbing; additional controls provide speed, quality reload, stop, 30-second skips, fullscreen, grid fullscreen, picture-in-picture, and return to live.
- Volume changes are saved automatically per web account, platform and streamer, including 0%. Reopening a stream, changing quality, and reloading the page restore the saved level before playback starts. Live, replay and downloaded videos with the same resolved channel share its volume. Inactive-player muting does not change the saved level. Signing in as the same user on another device loads that user's saved volumes; clearing browser site data does not erase them.
- Provider replay/DVR uses the existing replay resolver, including its availability and account requirements. Ordinary browser HLS seeking is limited to the media that the provider makes available; it does not create a recording buffer.
- VOD resume, completion, and watched history share the desktop history service. Progress is checkpointed during playback and on seek, pause and close.
- Live chat read/send, emotes and badges, with per-user docked/overlay/hidden layout, font size and opacity. Drag the overlay's lower-left corner to resize it; background opacity can reach 0% while messages remain visible. Provider catalogs resolve Twitch/Kick badges and animated emotes for live and replay chat. See [overlay controls and verification](web-chat-overlay-2026-10-21.md). Archive chat uses the existing paged VOD chat provider and follows the browser's playback position. Twitch prediction display and authorized create/lock/cancel/resolve actions use the same chat client as desktop playback.
- Live clip creation and follow/unfollow use the desktop account services. A confirmed clip is offered as a link. Website sign-in requests, when needed, appear on the Windows host.
- The shared download library can enqueue VODs, show progress, retry, cancel, delete with confirmation, and play completed HLS or MP4 packages in the browser. Storage and conversion jobs remain on the host; download format, bandwidth and folder are managed through desktop settings.
- Past broadcasts and Downloads show each VOD's publication date and sort newest first, including after loading another page. Download cards retain provider thumbnails and publication metadata; older library entries look up missing metadata from the provider. Unavailable dates sort last and show “Publication date unavailable.” Missing or failed artwork uses the card placeholder.
- Browser playback defaults, chat appearance and per-channel geometry, keyboard shortcuts, inactive-player behavior and volumes belong to the signed-in web user. The browser uses the host's connected provider accounts. Account setup/import, executable paths, filesystem locations, application updates, Windows hotkeys, tray behavior, native VLC renderer/overlay settings and Windows notifications remain desktop administration. Follows, downloads and watch history are shared with the desktop. Automatic followed-channel bonus workers continue running on the host.

### Overlay chat

In the browser, open **Preferences > Chat appearance** and choose **Over the video**. Changes save automatically to the signed-in web account. Drag **Move chat** to reposition the overlay; drag its lower-left corner to resize. Focus either handle to use arrow keys, Shift for larger steps, or Home to reset position or size. Escape cancels a drag. Position and dimensions save per channel within the web account; text size and opacity save for that account. The chat button temporarily hides or shows a player's chat. Switching layouts preserves messages and an unsent draft.

The overlay sits inside the video's surface, including in multi-stream and fullscreen layouts. Its default size leaves room for media controls, and you can move or resize it all the way to the video's bottom edge. Connection failures remain visible. Use the player's **Fullscreen** button (or the toolbar's grid fullscreen button) to keep chat with the video. These buttons are available when the browser supports page fullscreen. The video-only fullscreen control is suppressed when page fullscreen is available and the browser supports `controlslist="nofullscreen"`; native video-only fullscreen and picture-in-picture cannot display the surrounding page's chat. See [Chrome's media controls documentation](https://developer.chrome.com/blog/chrome-58-media-updates?hl=en).

The `local web: overlay` browser regression uses actual HTTPS-served assets, decoded HLS video, trusted pointer clicks, and deterministic live/replay chat fixtures. It covers phone widths, grid/player fullscreen, sending, connection errors, hide/show, layout switching, appearance settings, page reload and replay seeking. Screenshots are written to `.artifacts/local-web-design/overlay-*.png`. These fixtures do not establish physical TV/phone/Linux browser compatibility or live provider connectivity.

## Security boundary

- Kestrel binds the **exact selected IPv4 address**, never `0.0.0.0`, `[::]`, a hostname wildcard or a proxy endpoint. Only currently connected Ethernet/Wi-Fi interfaces with RFC 1918 addresses and usable `/8`–`/30` prefixes are offered. Public, tunnel-type, link-local, IPv6 and unrelated private subnets are excluded. A virtual/VPN adapter that identifies itself as Ethernet must not be selected as the shared home LAN.
- Every request checks the actual socket peer against the selected interface's subnet, verifies that the interface/address/prefix is still current, requires TLS, and checks the exact Host and Origin. IPv4-mapped addresses are normalized. Network/broadcast client addresses are rejected. Forwarded headers never establish client identity; no proxy middleware, CORS allowance, UPnP, router mapping or automatic firewall exception is installed.
- This protects the application's network boundary; it cannot identify the original sender behind a router that deliberately source-NATs Internet traffic into an allowed LAN address. Do not forward this port. If Windows Firewall blocks a device, restrict any manually added exception to the **Private** profile and **local subnet**. Guest Wi-Fi isolation can also prevent connectivity.
- Usernames are unique without regard to case. Passwords must contain 12–128 characters and are saved only as separate random-salt PBKDF2-HMAC-SHA-256 hashes with 600,000 iterations. Hash comparisons use constant time. Five login attempts per device per five minutes and thirty attempts globally per five minutes are allowed, including successful attempts. The limiter's device table is bounded. Passwords are never accepted in URLs or logged.
- Successful sign-in creates a cryptographically random 256-bit session identifier in a `Secure`, `HttpOnly`, `SameSite=Strict`, `__Host-` cookie. Sessions bind to the connecting IP, expire after 30 minutes without activity or eight hours absolutely, and are capped at 32. Changing a password or removing an account revokes that user's sessions; **Disconnect all devices** revokes all sessions. Logout and expiration release owned players/chat/offline leases. Expired sessions cannot authorize requests while cleanup runs.
- Mutations require JSON, the same Origin, a custom application header, and a session-specific CSRF token. GET/HEAD media routes do not change account or library state. Content Security Policy, frame restrictions, MIME sniffing protection, no-referrer and no-store headers apply. Metadata/chat is rendered with DOM text nodes; no provider text is inserted as HTML.
- Media routes accept opaque resource IDs, scoped to a device's workspace and player. There is no arbitrary URL or file-path endpoint. Every remote connection and redirect requires public HTTPS on the normal port without embedded credentials. DNS results must all be public; the connection callback connects to the **same validated IP**, so DNS rebinding cannot switch the target to a private address. System proxy settings and upstream cookies are disabled. Certificate validation retains the normal TLS hostname check.
- HLS rewriting includes URI attributes for variants, audio, keys and initialization sections. Local/data/HTTP URLs, private literal addresses, malformed URI fields, content steering and variable substitution fail closed. Manifest/resource/segment sizes and counts, connections, API concurrency, body sizes and operation deadlines are bounded. Offline playback uses an acquired, validated download generation and its exact file inventory, with junction/symlink checks. The subscriber-only resolver's app-generated local manifest is read only through an explicit trusted path and may reference remote public media only.
- Neither account secrets, local paths nor raw provider exceptions are returned by the settings/download/error APIs. The web host has no request logging provider. The server's public assets, including hls.js, are embedded and served locally; there is no runtime JavaScript CDN dependency.

## Dependencies and validation

The implementation uses the existing .NET 10 ASP.NET Core Kestrel runtime; self-contained distribution includes that framework. Framework-dependent development runs require the matching ASP.NET Core shared runtime as well as the desktop runtime. Endpoint/TLS implementation follows [Microsoft's Kestrel endpoint documentation](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/servers/kestrel/endpoints?view=aspnetcore-10.0); mutation protection follows the principles in [Microsoft's CSRF documentation](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0).
